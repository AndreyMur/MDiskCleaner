## Согласованность с PRD

План покрывает все функциональные требования FR-1.1–1.13 и критерии приёмки (раздел 7 PRD). ## Фазы реализации

### Фаза 1: Ядро сканирования кэшей и категоризация (Tracer Bullet)

**Цель:** Минимальный сквозной путь «путь → объект очистки» для известных кэшей и Temp: фактический путь (npm), размер, категория, риск. На этом ядре строится весь модуль.

**Затрагивает:** backend

**Задачи:**
- [ ] Модель `CleanupItem` (путь, размер, категория, уровень риска, признак «требует админа», признак IN_USE, список дочерних объектов) и перечисления категорий/риска в ядре Core (раздел 2 PRD).
- [ ] Сканер размеров: параллельный обход каталогов на P/Invoke Win32 `FindFirstFile`/`FindNextFile`, суммирование длин файлов, пропуск недоступных веток с записью в журнал (SilentlyContinue), таймаут на ветку с продолжением остальных; `Task`, `IProgress<ScanProgress>`, `CancellationToken` (FR-1.3, FR-1.4).
- [ ] Справочник известных путей категорий Cache/Temp/updater относительно `%LOCALAPPDATA%`, `%APPDATA%`, `%USERPROFILE%`, `%ProgramData%`, `%ProgramFiles%` (npm, pip, uv, pnpm-cache, dotslash, .gradle, .rustup, .cargo, ms-playwright, Temp, VS Code кэши, `*-updater`) + определение фактического пути npm через `npm config get cache` и `~/.npmrc` (раздел 4 PRD, приёмка «D:\npm-cache»).
- [ ] `CategorizationService`: чистая логика «категория + риск» — Cache/Temp/`*-updater` — низкий, тулчейны/SDK — средний, папки программ и пользовательские данные — высокий (не предлагать к автоудалению); действие по умолчанию, выводимое из риска (FR-1.6).
- [ ] Тесты: unit — категоризация/риск/действие по умолчанию; integration на временных каталогах — размеры, пропуск недоступных веток, таймаут ветки, фактический путь npm через фиктивный `.npmrc`.

**Когда готова:** smoke-прогон на эталонной машине выводит объекты плана для кэшей: npm показывает фактический путь (D:\npm-cache) с размером ~14,5 ГБ; скан известных кэшей ≤ 30 с; тесты зелёные.

### Фаза 2: Полный скан диска, системные исключения, детализация и инкрементальный кэш

**Цель:** Распространить анализ на весь выбранный диск: размеры каталогов верхнего уровня и подкаталогов известных категорий, системные объекты, детализация крупных тулчейнов; повторные сканы быстрые за счёт инкрементального кэша.

**Затрагивает:** backend, database (инкрементальный кэш скана в `%LOCALAPPDATA%\DiskCleaner\scancache`)

**Задачи:**
- [ ] Скан диска по выбору (по умолчанию системный): суммарные размеры каталогов верхнего уровня и подкаталогов известных категорий; игнор-список системных каталогов (`Windows`, `System Volume Information`, `$Recycle.Bin`, `Program Files\WindowsApps`) по умолчанию + флаг «включить» (FR-1.1, FR-1.2, FR-1.4).
- [ ] Системные объекты: размер Корзины и `hiberfil.sys` (категория SystemFile, через powercfg/атрибуты) с риском «низкий» (FR-1.6, раздел 4 PRD).
- [ ] Детализация крупных объектов: Android SDK (NDK/system-images/platforms/emulator), `.gradle` (caches/wrapper/dists/jdks — jdks только с согласия), VS Code (Cache/CachedData/CachedExtensionVSIXs/Crashpad/GPUCache/logs/WebStorage, без User/) (FR-1.5).
- [ ] Инкрементальный кэш результатов обхода по веткам (mtime каталога + размер) в scancache — повторный скан пересчитывает только изменённые ветки; UTF-8 в файлах, логе и выводе (NFR).
- [ ] Тесты: integration на временных деревьях — игнор-список и его включение, детализация (Android SDK/.gradle), пересчёт только изменённых веток по mtime; замер времени скана на эталонной машине.

**Когда готова:** Полный скан C: ≤ 5 минут (цель ≤ 3 минут); крупные объекты эталонного отчёта (npm 14,5 ГБ, .gradle 13,3 ГБ, Android SDK 14 ГБ, updater-папки) детализированы и корректно категоризированы — ≥ 90% объектов из отчёта эталонной очистки; повторный скан пересчитывает только изменённые ветки.

### Фаза 3: Реестр Uninstall, дубли, «подозрительные» записи и признак IN_USE

**Цель:** Подключить инвентаризацию установленного ПО (объекты InstalledApp для плана удаления), поиск дублей и подозрительных записей, а также защиту от включения в авто-план используемых объектов.

**Затрагивает:** backend, database (реестр — три ветки Uninstall)

**Задачи:**
- [ ] Загрузка и нормализация ПО из трёх веток Uninstall (`HKLM`, `HKLM\Software\WOW6432Node`, `HKCU`) через `Microsoft.Win32.Registry` в модель `InstalledApp`: DisplayName, Publisher, EstimatedSize, InstallDate, DisplayVersion, InstallLocation, UninstallString, ProductCode (FR-1.8).
- [ ] Вычисление размера ПО: `EstimatedSize` против фактического размера `InstallLocation`, где каталог доступен (FR-1.8).
- [ ] Эвристика дублей: одинаковые DisplayName/Publisher при разных версиях (два JDK, два Windows SDK, VS Build Tools 2019+2022) — предлагать удаление старых, помечая версию и дату установки (FR-1.9).
- [ ] «Подозрительные» записи: некорректный Publisher, `${PRODUCT_PUBLISHER}`, странные домены → флаг `Review manually` (FR-1.10).
- [ ] Детектор IN_USE: сверка ExecutablePath запущенных процессов (`System.Diagnostics.Process`/WMI) с путями объектов — пометка `IN_USE` и исключение из авто-плана (FR-1.7). Тесты: unit — эвристики дублей и подозрительных записей на фикстурах; integration — чтение изолированной ветки HKCU, пометка IN_USE для временного каталога с запущенным процессом.

**Когда готова:** На эталонной машине найдены дубли (JDK, Windows SDK) с версиями и датами установки; запущенный `adb.exe` из Android SDK помечает SDK как `IN_USE`; подозрительные записи помечены `Review manually`.

### Фаза 4: Экран «План очистки» (GUI)

**Цель:** Тонкий GUI поверх ядра: выбор диска, анализ с прогрессом и отменой в фоне, дерево категорий, сводка и таблица плана без бизнес-логики в представлении.

**Затрагивает:** frontend (WPF + MVVM)

**Задачи:**
- [ ] Экран анализа: выбор диска/источника, кнопка «Анализ», прогресс и отмена (`IProgress`, `CancellationToken`) в фоновых задачах без блокировки UI; переключатель «включить системные каталоги» (FR-1.1, FR-1.2).
- [ ] Дерево категорий с размерами: раскрывающиеся группы по категориям, сводка «размер × число объектов» по каждой категории (FR-1.11).
- [ ] Таблица плана (DataGrid): имя, размер, риск, «требует админа?», действие по умолчанию (очистить / не трогать / спросить); метки `IN_USE` и `Review manually` (FR-1.11).
- [ ] ViewModel-и (MVVM) поверх данных ядра; GUI не содержит бизнес-логики (архитектура PRD 00).
- [ ] Тесты: unit ViewModel-ей (агрегация категорий, отображение меток/действий по умолчанию); smoke-тест экрана на синтетических данных.

**Когда готова:** На эталонной машине GUI показывает сводку по категориям и таблицу плана с суммарной оценкой ~57 ГБ и детализацией категорий; анализ не «подвешивает» UI, отмена работает.

### Фаза 5: Экспорт плана и снапшоты скана (backend)

**Цель:** Тестируемые генераторы экспорта и хранение предыдущего скана для сравнения «было/стало».

**Затрагивает:** backend, database (снапшоты в `%LOCALAPPDATA%\DiskCleaner\scancache`)

**Задачи:**
- [ ] Экспорт JSON: `System.Text.Json`, единая схема плана (категории, объекты, размеры, риски) (FR-1.12).
- [ ] Собственные генераторы Markdown и CSV для экспорта плана (FR-1.12).
- [ ] Сохранение предыдущего скана (снапшот категорий/объектов) в scancache; загрузка и расчёт сравнения «было/стало» (FR-1.13).
- [ ] UTF-8 во всех файлах вывода (корректность кириллицы в путях и названиях, NFR).
- [ ] Тесты: golden-файлы экспорта (валидность, кириллица), round-trip снапшота, расчёт дельты «было/стало».

**Когда готова:** Экспорты корректно открываются во всех трёх форматах (UTF-8); снапшот сохраняется и после повторного скана строится сравнение «было/стало».

### Фаза 6: Интеграция экспорта и сравнения в GUI (frontend)

**Цель:** Отдать пользователю экспорт плана и раздел сравнения с предыдущим сканом в GUI.

**Затрагивает:** frontend (WPF + MVVM)

**Задачи:**
- [ ] Кнопка «Экспорт» с выбором формата (Markdown/JSON/CSV) и диалогом сохранения (FR-1.12).
- [ ] Раздел «Было/стало» на экране плана: сравнение с предыдущим сканом (FR-1.13).
- [ ] Тесты: unit ViewModel-ей — выбор формата и пути сохранения, отображение дельты сравнения.

**Когда готова:** Из GUI экспортируются все три формата; раздел «Было/стало» показывает результат повторного скана; тесты зелёные.

## Критерии приёмки PRD (раздел 7) и их покрытие

- **≥ 90% объектов эталонного отчёта найдено и категоризировано** — Фазы 1–3, проверка на эталонной машине после Фазы 3.
- **npm показывает фактический путь кэша (D:\npm-cache)** — Фаза 1.
- **Объект с запущенным процессом помечается IN_USE** — Фаза 3.
- **Сумма размеров плана сходится с фактически освобождённым местом ± 10% (57 ГБ)** — Фаза 2 (точность размеров) + проверка совместно с исполнением плана модуля 02 (PRD 02) на эталонном прогоне.
