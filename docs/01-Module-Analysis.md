# PRD 01 — Модуль «Анализ диска и категоризация»

- **Версия:** 1.0
- **Дата:** 2026-09-06
- **Относится к:** PRD 00 (G1, FR-0.1, FR-0.2)

## 1. Назначение

Модуль сканирует диск(и) и строит категоризированный список «объектов очистки» с размерами, риском и оценкой экономии — основу для плана очистки.

## 2. Термины

- **Объект очистки (CleanupItem):** путь (файл или каталог), размер, категория, уровень риска, признак «требует админа», список дочерних объектов.
- **Категория:** Cache / Leftover / DevToolchain / InstalledApp / SystemFile / Temp / UserData.
- **Dry-run:** режим, в котором объект показан, но не удаляется.

## 3. Источники информации (на основе реального анализа)

1. Размеры каталогов рекурсивным обходом (`Get-ChildItem`/Win32 API FindFirstFile, параллельно по подкаталогам).
2. Перечень установленного ПО: реестр
   - `HKLM\...\Uninstall\*`, `HKLM\Software\WOW6432Node\...\Uninstall\*`, `HKCU\...\Uninstall\*`
   - поля: DisplayName, Publisher, EstimatedSize, InstallDate, DisplayVersion, InstallLocation, UninstallString, PSChildName (ProductCode).
3. Кэши по известным путям (справочник путей и их принадлежности менеджерам).
4. Конфигурация менеджеров (напр., реальный путь npm-кэша из `npm config get cache` или `~/.npmrc`) — чтобы не чистить несуществующий кэш и не пропускать перенаправленный на другой диск.
5. Список запущенных процессов и их ExecutablePath — для определения «используется сейчас».

## 4. Справочник известных путей (v1.0)

Источник — реально найденные объекты; пути относительно `%LOCALAPPDATA%`, `%APPDATA%`, `%USERPROFILE%`, `%ProgramData%`, `%ProgramFiles%`.

| Категория | Путь/маска | Примечание |
|---|---|---|
| Cache | `Local\npm-cache`, путь из `npm config get cache` | кэш npm |
| Cache | `Local\pip`, `Local\uv`, `Local\pnpm-cache`, `Local\dotslash` | кэши Python/Node-менеджеров |
| Cache | `.gradle\caches`, `.gradle\wrapper\dists`, `.gradle\jdks` | Gradle; jdks — только с согласия |
| Cache | `.rustup`, `.cargo` | тулчейн Rust (категория DevToolchain/Cache) |
| Cache | `Local\ms-playwright` | браузеры Playwright |
| Cache | `Local\Temp\*`, `Windows\Temp\*` | Temp |
| Cache | `Roaming\Code\{Cache,CachedData,CachedExtensionVSIXs,Crashpad,GPUCache,logs,WebStorage}` | кэши VS Code (не удалять User/) |
| Leftover | `Local\*-updater`, `Local\Programs\*-updater` | остатки апдейтеров |
| Leftover | каталоги Program Files без записи в Uninstall | осиротевшие папки |
| Leftover | `Local\Google\AndroidStudio*`, `.android` | конфиг удалённой IDE |
| Leftover | `ProgramData\*` брендированные папки удалённых продуктов | по справочнику |
| DevToolchain | `Local\Android\Sdk` | NDK/system-images/emulator (детализация) |
| SystemFile | `C:\hiberfil.sys` | через powercfg |
| InstalledApp | записи Uninstall | только для плана удаления |

## 5. Функциональные требования

### Сканирование
- FR-1.1: Сканировать выбранный диск (по умолчанию системный). Показывать прогресс и отмену.
- FR-1.2: Игнорировать системные каталоги по умолчанию: `Windows`, `System Volume Information`, `$Recycle.Bin`, `Program Files\WindowsApps` (только по явному выбору). Дать возможность включить.
- FR-1.3: Параллельное сканирование независимых веток; таймаут на ветку с продолжением остальных (реальный кейс: полный скан C: превысил 5 минут → нужен прогресс и распараллеливание).
- FR-1.4: Для каждого каталога верхнего уровня и подкаталогов известных категорий вычислять суммарный размер (аккуратно с Recycle Bin и правами доступа — `SilentlyContinue`).
- FR-1.5: Детализировать крупные объекты: для Android SDK показать NDK/system-images/platforms; для `.gradle` — caches/wrapper/jdks.

### Категоризация и риск
- FR-1.6: Присваивать риск:
  - Низкий: кэши (регенерируются), Temp, Корзина, hiberfil (через powercfg), `*-updater`.
  - Средний: тулчейны/SDK/дубли ПО (перекачиваются/переустанавливаются, требует согласия).
  - Высокий: папки программ, пользовательские данные (никогда не предлагать к автоудалению).
- FR-1.7: Определять признак «используется»: наличие запущенного процесса с путём внутри объекта (пример: `adb.exe` из `Android\Sdk` блокировал удаление SDK). Такие объекты помечать `IN_USE` и исключать из авто-плана.

### Работа с реестром
- FR-1.8: Загружать список ПО из трёх веток Uninstall; нормализовать; вычислять размер (EstimatedSize) и фактический InstallLocation.
- FR-1.9: Находить дубли: одинаковый DisplayName/Publisher при разных версиях (пример: два JDK, два Windows SDK, VS Build Tools 2019+2022). Предлагать удаление старых, помечая версию и дату установки.
- FR-1.10: Идентифицировать «подозрительные» записи (некорректные Publisher, `${PRODUCT_PUBLISHER}`, странные домены) и помечать флагом `Review manually`.

### Выход
- FR-1.11: Экран «План очистки»: сводка по категориям (размер, число объектов), раскрывающиеся группы, колонки: имя, размер, риск, админ?, действие по умолчанию (очистить/не трогать/спросить).
- FR-1.12: Экспорт плана: Markdown/JSON/CSV.
- FR-1.13: Сохранение предыдущего скана для сравнения «было/стало».

## 6. Нефункциональные требования

- Полный скан C: 136 ГБ — ≤ 5 минут (цель ≤ 3 мин), скан известных кэшей — ≤ 30 с.
- Инкрементальность: кэшировать результаты обхода по веткам (mtime каталога), при повторном скане пересчитывать только изменённые.
- Чтение размера каталога не должно «подвешивать» UI — фоновые задачи.
- Кодировка вывода в консоль/файлы — UTF-8 (реальный кейс: русские имена и OEM-кодировка ломали вывод).

## Стек и реализация (в рамках PRD 00)

- Сканирование — сервис `ScanService`: параллельный обход веток (`Parallel.ForEachAsync`), рекурсия по каталогам через `Directory.EnumerateFileSystemEntries`; для скорости и путей > MAX_PATH — P/Invoke Win32 `FindFirstFile`/`FindNextFile`. Фоновые `Task` + `IProgress<ScanProgress>` + `CancellationToken`, UI не блокируется (FR-1.1–1.3).
- Размеры каталогов — суммирование длин файлов; `UnauthorizedAccessException` и системные ветки — пропуск с записью в журнал («SilentlyContinue»-семантика), FR-1.4.
- Реестр — `Microsoft.Win32.Registry`: три ветки Uninstall (`HKLM`, `WOW6432Node`, `HKCU`), нормализация в модель `InstalledApp` (FR-1.8). Дубли и «подозрительные» записи — эвристики `CategorizationService` (FR-1.9–1.10).
- Категоризация и риск — чистая логика в ядре (`CleanupItem`), unit-тесты; признак `IN_USE` — сверка путей с ExecutablePath процессов (`System.Diagnostics.Process`, WMI), FR-1.6–1.7.
- GUI: дерево категорий (TreeView) и таблица плана (DataGrid) строятся из плана ядра без бизнес-логики (FR-1.11).
- Экспорт — `System.Text.Json` (JSON), собственные генераторы Markdown/CSV (FR-1.12); инкрементальный кэш веток (mtime + размер) — JSON в `%LOCALAPPDATA%\DiskCleaner\scancache` (FR-1.13).
- Кодировка вывода — UTF-8 везде (файлы, лог, stdout команд менеджеров).

## 7. Критерии приёмки

- На эталонной машине модуль находит и корректно категоризирует ≥ 90% объектов из фактического отчёта очистки (14,5 ГБ npm-cache, 13,3 ГБ .gradle, 14 ГБ Android SDK, updater-папки и т.д.).
- Для npm показывает фактический путь кэша (D:\npm-cache), а не только `Local\npm-cache`.
- Объект с запущенным процессом помечается IN_USE.
- Сумма размеров плана сходится с фактически освобождённым местом ± 10% (на эталонном прогоне 57 ГБ).
