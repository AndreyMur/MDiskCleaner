# Plan: Модуль «Кэш-клинер»

**PRD:** 02-Module-CacheCleaner
**Дата:** 2026-09-06

## Согласованность с PRD

План покрывает FR-2.1–2.12 и критерии приёмки (раздел 7 PRD). Размеры кэшей и категория Cache приходят из модуля 01 (PRD 01); исполнение встроено в экран «План очистки» M1 (plan-00). Открытые вопросы PRD (раздел 8: Docker/WSL, политика CI/оффлайн) в план не включены. Категория Leftover (`*-updater`, конфиги удалённых приложений) не является частью этого модуля — обрабатывается модулем 03 (FR-2.9).

## Фазы реализации

### Фаза 1: Справочник кэшей и определение реальных путей (Tracer Bullet)

**Цель:** Минимальный путь «конфигурация менеджера → фактический путь кэша»: определить реальные пути (в т.ч. на другом диске), распознать осиротевший кэш и не создавать объекты для несуществующих путей. Фундамент для всех остальных фаз.

**Затрагивает:** backend

**Задачи:**
- [ ] Справочник кэшей как конфигурация (JSON/embedded) на менеджера: дефолтные пути, команда определения реального пути, штатная команда очистки, «прямой» путь удаления, подпапки и уровень согласия (структура под FR-2.10–2.11). Покрыть все кейсы из раздела 2 PRD: npm, Gradle (`caches`/`wrapper\dists`/`jdks`/`daemon`), Rust (`.rustup`/`.cargo`), Playwright, uv, pip, pnpm, dotslash, VS Code.
- [ ] Определение фактического пути кэша: запуск команды менеджера через `ProcessStartInfo` (аргументы без шелл-строк, `RedirectStandardOutput`, UTF-8), например `npm config get cache`, либо чтение конфига (`.npmrc`); фолбэк на путь по умолчанию (FR-2.2).
- [ ] Обнаружение «осиротевшего» кэша: известный путь существует и содержит данные, но менеджер его больше не использует (кейс `C:\...\Local\npm-cache` 14,5 ГБ при конфиге `D:\npm-cache`) (FR-2.4).
- [ ] Пути вне сканируемого диска учитывать отдельно, не пропускать (FR-2.3); для несуществующего пути объект очистки не создавать (приёмка «не чистить несуществующий кэш»).
- [ ] Тесты: unit — разбор вывода/конфига и резолвинг реального пути (npm на другом диске), кириллица (UTF-8); integration — фиктивные `.npmrc`/окружение, распознавание осиротевшего кэша.

**Когда готова:** Smoke-прогон на реальном окружении находит фактический путь npm (`D:\npm-cache`) и осиротевший `C:\...\npm-cache` 14,5 ГБ; для всех менеджеров реальных кейсов справочник даёт валидный набор путей; тесты зелёные.

### Фаза 2: Планировщик действий очистки

**Цель:** Для каждого кэша решить «чем и с каким согласием чистить», подготовить пользователю информацию для подтверждения и защитить от лишней/опасной очистки.

**Затрагивает:** backend

**Задачи:**
- [ ] Карточка действия для каждого кэша: штатная команда (если есть), оценка экономии (размер из PRD 01), «что произойдёт после очистки», оценка времени/трафика на восстановление (FR-2.1, FR-2.5).
- [ ] Логика выбора способа: приоритет штатной команды; прямое удаление каталога — как fallback (FR-2.6); если после штатной команды размер не изменился/изменился незначительно — предлагать прямое удаление (FR-2.7; план решения, исполнение — Фаза 3).
- [ ] Защитный режим «не трогать кэши при < 15% свободного места» — проверка `DriveInfo.AvailableFreeSpace` перед формированием плана (FR-2.12).
- [ ] Правила исключений и согласия: Gradle — отдельные действия для `caches`/`wrapper\dists`/`jdks`/`daemon` с разным уровнем согласия (FR-2.11); VS Code — только перечень кэш-подпапок (Cache, CachedData, CachedExtensionVSIXs, Crashpad, GPUCache, logs, WebStorage), никогда `User/`, `extensions/`, `settings.json` (FR-2.10); `*-updater` и конфиги удалённых приложений не показывать — категория Leftover (FR-2.9).
- [ ] Тесты: unit — матрица решений «команда vs прямое удаление», порог свободного места (FR-2.12), split Gradle, whitelist-защита VS Code.

**Когда готова:** Планировщик выдаёт действия с последствиями и корректным уровнем согласия; при < 15% свободного места кэши помечаются «не трогать»; тесты зелёные.

### Фаза 3: Исполнение штатных команд и контроль результата

**Цель:** Очистка штатными командами менеджеров с контролем exit-кода и фактического результата; честный fallback на прямое удаление.

**Затрагивает:** backend

**Задачи:**
- [ ] Запуск штатной команды через `ProcessStartInfo` (аргументы без шелл, перехват exit-кода и stdout/stderr, UTF-8): кэши пользователя и `rustup self uninstall` — в контексте пользователя без админа; глобальные менеджеры из Program Files — запуск с UAC-подъёмом (`Verb = "RunAs"`, полная elevated-инфраструктура — M2) (раздел 5 PRD).
- [ ] После команды — повторное измерение размера кэша; если размер не изменился/изменился незначительно — пометить объект «требует прямого удаления» и предложить его (реальный кейс `npm cache clean` с exit 0) (FR-2.7).
- [ ] Проверка IN_USE перед действием (запущенные процессы из каталога, механизм PRD 01/05): используемые объекты откладывать и не включать в авто-план (FR-2.8).
- [ ] Журнал действия: что удалено/что пропущено и причина (NFR).
- [ ] Тесты: integration — фиктивные команды-менеджеры с разными exit-кодами/выводом, перепроверка размера и метка fallback, откладывание IN_USE; unit — разбор выходных данных команд.

**Когда готова:** На временных кэшах штатная команда исполняется с контролем exit-кода; при exit 0 и неизменившемся размере объект помечается «требует прямого удаления»; всё логируется; IN_USE-объекты отложены.

### Фаза 4: Прямое удаление каталогов кэшей

**Цель:** Быстрое и безопасное удаление каталогов кэшей (в т.ч. осиротевших) с прогрессом и dry-run — закрывает основной объём M1 (~30–35 ГБ).

**Затрагивает:** backend

**Задачи:**
- [ ] Прямое удаление каталога `Directory.Delete(path, recursive: true)` с прогрессом; для каталогов > 1 ГБ — удаление параллельными партиями; удаление 14,5 ГБ ≤ 3 минут (NFR, FR-2.6 fallback).
- [ ] Удаление «осиротевшего» кэша по известному пути, даже если менеджер его больше не использует (FR-2.4).
- [ ] VS Code: удалять только кэш-подпапки из перечня; если VS Code запущен — отложить и показать пользователю предупреждение (FR-2.10).
- [ ] Dry-run: предпросмотр без удаления; полный журнал удалённого/пропущенного с причинами (NFR).
- [ ] Тесты: integration на временных каталогах — удаление крупного каталога партиями (замер времени), dry-run ничего не удаляет, пропуск заблокированных файлов с записью в журнал без прерывания плана.

**Когда готова:** Очистка осиротевшего npm-кэша 14,5 ГБ на эталонной машине ≤ 3 минут; при запущенном VS Code его кэши не удаляются и пользователь получает сообщение; dry-run не удаляет ничего; журнал фиксирует каждый объект.

### Фаза 5: Экран очистки кэшей в GUI (frontend)

**Цель:** Пользовательский сценарий M1: выбор кэшей чекбоксами, предпросмотр последствий, выполнение с подтверждением и отчёт — без «тихой» очистки.

**Затрагивает:** frontend

**Задачи:**
- [ ] Группы кэшей по менеджеру/приложению с размером, штатной командой и последствиями (FR-2.1, FR-2.5) на базе экрана «План очистки» модуля 01.
- [ ] Чекбокс на каждый объект — очистка только при явной отметке пользователя (NFR, G3); кэш вне сканируемого диска показывается отдельно с предложением очистки (FR-2.3).
- [ ] Dry-run-предпросмотр «что будет удалено» и подтверждение перед выполнением (NFR, G3).
- [ ] Выполнение плана с прогрессом; предупреждение для запущенного VS Code и IN_USE-объектов; отчёт «освобождено N ГБ / удалённое / пропущенное с причинами» (FR-2.8, FR-2.10, NFR).
- [ ] Тесты: unit ViewModel-ей (состояние чекбоксов, отображение последствий и предупреждений); e2e на эталонной машине — полный цикл очистки кэшей.

**Когда готова:** На эталонной машине через GUI воспроизводится очистка всех кэшей эталонного отчёта с суммарным эффектом ~35 ГБ, с подтверждением по каждому объекту, dry-run и отчётом.

## Критерии приёмки PRD (раздел 7) и их покрытие

- **Воспроизводит очистку всех кэшей эталонного отчёта (~35 ГБ суммарно)** — Фазы 1–5, e2e-проверка в Фазе 5.
- **npm: реальный путь (в т.ч. на другом диске), несуществующий кэш не «чистится»** — Фаза 1 (резолвинг) + Фазы 3–4 (fallback/удаление).
- **Запущенный VS Code: кэши не удаляются, пользователь получает сообщение** — Фаза 3 (IN_USE) + Фаза 4 (VS Code-правило) + Фаза 5 (сообщение в UI).
- **`npm cache clean --force` с exit 0 и неизменившимся размером → предлагается прямое удаление** — Фаза 2 (план) + Фаза 3 (перепроверка и метка).
