# Plan: Модуль «Сканер остатков (Leftover Scanner)»

**PRD:** 03-Module-LeftoverScanner
**Дата:** 2026-09-06

## Согласованность с PRD

План покрывает FR-3.1–3.8, требования безопасности (§5), NFR (§6) и критерии приёмки (раздел 7 PRD). Модуль входит в M2 (plan-00) и опирается на сервис реестра PRD 01 (белый список ПО), механизм проверки процессов PRD 01/05 и elevated-инфраструктуру M2 (PRD 05) для удаления из Program Files/ProgramData и Windows.old. Удаление пользовательских путей и dry-run используют общий движок исполнения плана (PRD 00).

| Фаза | FR | Затрагивает |
|---|---|---|
| Фаза 1 | FR-3.1, FR-3.2 | backend |
| Фаза 2 | FR-3.3, FR-3.4, FR-3.6; §5 (порог > 1 ГБ) | backend |
| Фаза 3 | FR-3.3/3.4 (проверки), FR-3.5; §5 (PATH, служба) | backend |
| Фаза 4 | FR-3.7, FR-3.8; §5 (UAC); NFR (журнал) | backend |
| Фаза 5 | FR-3.2–3.8 (GUI) | frontend |

## Фазы реализации

### Фаза 1: Белый список ПО и группа «Остатки апдейтеров» (Tracer Bullet)

**Цель:** Минимальный путь «папка → кандидат-остаток»: собрать белый список установленного ПО из реестра, просканировать верхние уровни ключевых каталогов, сопоставить и найти апдейтеры с размером и датой. Фундамент для всех эвристик модуля.

**Затрагивает:** backend

**Задачи:**
- [ ] Белый список установленного ПО из реестра Uninstall (переиспользование сервиса PRD 01): InstallLocation и нормализованный DisplayName для сопоставления (FR-3.1).
- [ ] Сканер верхних уровней (`GetDirectories`, без рекурсивного обхода) по `Program Files`, `Program Files (x86)`, `ProgramData`, `%LOCALAPPDATA%`, `%APPDATA%`, `%USERPROFILE%` — цель ≤ 60 с (NFR).
- [ ] Автоматическое сопоставление каталогов с белым списком по InstallLocation и по нормализованному имени; несопоставленные каталоги — кандидаты `LeftoverCandidate` (FR-3.1).
- [ ] Группа «Остатки апдейтеров» по маске `*-updater` (включая варианты `updater`, `update`, `_updater`): размер и дата последнего изменения для каждого каталога (FR-3.2).
- [ ] Тесты: unit — сопоставление с фикстурами реестра (по InstallLocation и по имени); integration — маска апдейтеров на временных каталогах, замер времени скана.

**Когда готова:** На эталонной машине найдены все 8 updater-папок (~1,8 ГБ) с размерами и датами изменения; скан остатков ≤ 60 с; ни одна папка установленного ПО из контрольного списка не помечена как кандидат.

### Фаза 2: Движок эвристик: конфиги удалённых программ и осиротевшие папки

**Цель:** Распределить остальные кандидаты по группам с автоматическим «основанием» (почему это остаток) и порогами, защищающими от ложных срабатываний.

**Затрагивает:** backend

**Задачи:**
- [ ] `LeftoverRuleEngine` со справочником брендов: конфиг-папки продуктов, «мусорные» бренды из ProgramData, Portable/вручную распакованные SDK как источник ложных срабатываний (алгоритм п.4, §5).
- [ ] Группа «Конфиги удалённых программ»: конфиг-каталог бренда в AppData (`Local\Google\AndroidStudio2025.3.2`, `.android`) при отсутствии установленного приложения и запущенных процессов — предложить удаление (FR-3.3).
- [ ] Группа «Осиротевшие папки Program Files/ProgramData»: только при (а) отсутствии записи Uninstall, (б) отсутствии процессов из этого пути, (в) малом размере или известном бренде; всегда требовать подтверждение (FR-3.4).
- [ ] Правило «пустые/почти пустые каталоги» и порог: папки > 1 ГБ без явной категории не предлагать к автоудалению (сначала анализ содержимого) (§5, п.4).
- [ ] Поле «основание» для каждого кандидата: нет в реестре / updater / конфиг удалённого продукта / нет процесса / пустой каталог (FR-3.6) + тесты эвристик и порогов.

**Когда готова:** На синтетических наборах кандидаты корректно распределены по группам с основаниями; найден конфиг удалённой Android Studio; папки > 1 ГБ без явной категории автоматически не предлагаются; тесты зелёные.

### Фаза 3: Проверки безопасности и Windows.old

**Цель:** Отсечь «живые» объекты (процессы, PATH, службы) и добавить системный остаток Windows.old с корректным определением прав.

**Затрагивает:** backend

**Задачи:**
- [ ] Проверка запущенных процессов из пути кандидата (механизм IN_USE, PRD 01/05): такие кандидаты не предлагать к удалению (FR-3.3, FR-3.4).
- [ ] Проверка вхождения пути кандидата в `%PATH%` и регистрации как службы (`sc query` / `ServiceController`) перед предложением/удалением (§5).
- [ ] Поиск `Windows.old*`: размер, способ удаления (Storage Sense / `cleanmgr` / DISM), удаление только с админ-правами (FR-3.5).
- [ ] Определение флагов для кандидатов: «требует админа» (Program Files/ProgramData/Windows.old) и «обязательное подтверждение» (FR-3.4, §5).
- [ ] Тесты: integration — временный каталог с запущенным процессом не предлагается; unit — проверка PATH и службы на фикстурах, Windows.old-фикстура с размером.

**Когда готова:** Кандидат, путь которого использует запущенный процесс, не предлагается; для Program Files/ProgramData/Windows.old проставлены флаги «требует админа» и обязательного подтверждения; тесты зелёные.

### Фаза 4: Исключения, dry-run и исполнение удаления

**Цель:** Управление исключениями пользователя, безопасный предпросмотр и подтверждённое исполнение удалений с фиксацией основания в журнале.

**Затрагивает:** backend

**Задачи:**
- [ ] Хранилище исключений `exclusions.json` в `%LOCALAPPDATA%\DiskCleaner`: исключение по пути и по бренду; кандидаты из исключений не появляются в плане (FR-3.7).
- [ ] Модель плана «все кандидаты выключены по умолчанию» (FR-3.8, модель PRD 00) и dry-run-предпросмотр без удаления (FR-3.8).
- [ ] Исполнение подтверждённых удалений: пользовательские пути — в контексте пользователя; Program Files/ProgramData/Windows.old — через elevated-процесс (инфраструктура M2, PRD 05) одним UAC-подъёмом; перед каждым удалением повторные проверки процессов/PATH/службы из Фазы 3 (FR-3.4, FR-3.5, §5).
- [ ] Журнал исполнения с фиксацией основания удаления для каждого объекта (NFR, FR-3.6).
- [ ] Тесты: исключения (путь/бренд), dry-run ничего не удаляет, формирование elevated-сценария для PF-кандидата, журнал с основаниями.

**Когда готова:** Кандидат из `exclusions.json` не появляется в плане; dry-run ничего не удаляет; для Program Files формируется elevated-сценарий; журнал фиксирует основание удаления для каждого объекта.

### Фаза 5: Экран остатков в GUI (frontend)

**Цель:** Показать остатки пользователю в понятных группах с основаниями, дать точечное включение (по умолчанию всё выключено) и управление исключениями.

**Затрагивает:** frontend

**Задачи:**
- [ ] Группы остатков в дереве/плане (на базе экрана PRD 01): апдейтеры, конфиги удалённых программ, осиротевшие Program Files/ProgramData, Windows.old — размер, дата, «почему это остаток» (FR-3.2–3.6).
- [ ] Все кандидаты «выключены» по умолчанию, включение чекбоксом; опасные объекты (Program Files/ProgramData/Windows.old) — обязательное пообъектное подтверждение (FR-3.8, §5).
- [ ] Dry-run-предпросмотр плана остатков (FR-3.8).
- [ ] Кнопка «Добавить в исключения» для пути или бренда (FR-3.7); отображение админ-шагов с подтверждением UAC.
- [ ] Тесты: unit ViewModel-ей (состояние чекбоксов, исключения); e2e на эталонной машине — контрольный список установленного ПО не предлагается к удалению.

**Когда готова:** GUI показывает 8 updater-папок (~1,8 ГБ) и конфиг Android Studio; ни одна папка действующего приложения не предлагается; шаги Program Files/ProgramData требуют подтверждение и UAC.

## Критерии приёмки PRD (раздел 7) и их покрытие

- **Находит все 8 updater-папок (~1,8 ГБ) и конфиг Android Studio** — Фаза 1 (updater-маска) + Фаза 2 (конфиги удалённых программ), проверка на эталонной машине в Фазе 5.
- **Не предлагает удалить ни одну папку действующего приложения** — Фаза 1 (сопоставление с белым списком) + Фаза 3 (проверки процессов/PATH/службы), e2e в Фазе 5.
- **Корректно требует админ-права и подтверждение для Program Files/ProgramData** — Фаза 3 (флаги) + Фаза 4 (elevated-исполнение) + Фаза 5 (подтверждение в UI).
